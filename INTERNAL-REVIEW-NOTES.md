# Internal review notes — not for publication

This site was drafted from a real, code-verified inventory of what each product actually does (see the audit that produced `data/apps.json`), using generic-but-standard legal language for the parts that are business decisions rather than facts about the code. It is a solid working draft, not a substitute for a lawyer's sign-off before you rely on it in a real dispute or regulatory inquiry. Items to specifically revisit:

1. **Grievance Officer is named by role, not by person.** DPDP Rules expect a named Grievance Officer with contact details. Right now every page points to `support@animocentric.com` / the LLP's general phone and address, framed as "our Grievance Officer," without naming an individual. If you want to name a specific person, update `entity.json` (add a `grievanceOfficerName` field and wire it into `build.js`) — I left it role-based rather than inventing a name.

2. **Refund/cancellation terms are generic.** "Fees already paid are non-refundable, except where required by law" and "non-refundable once the veterinarian has responded" are standard-shape clauses, not numbers you gave me (e.g. no specific refund window, no partial-refund tiers for subscriptions). If you have (or want) a specific refund policy, that should replace the generic language in `data/apps.json` under each app's `terms` block.

3. **Dispute resolution is court jurisdiction only — no arbitration clause.** I set governing law to India with exclusive jurisdiction of Hyderabad/Telangana courts. Many SaaS platforms add a mandatory arbitration clause instead (or in addition). That's a real strategic choice (cost, speed, enforceability) worth a lawyer's input rather than something to default silently.

4. **[UPDATED 2026-09-18, then DRAFTED 2026-09-18] International users are no longer hypothetical, and the site now carries generic GDPR/CCPA-shaped text for them — same "solid working draft, not a lawyer's sign-off" caliber as the rest of this site, not a compliance guarantee.** The platform now actively supports non-India clinics end to end: a country picker at signup (India, US, UK, Ireland, Germany, France, Spain, Italy, Netherlands, Portugal, Australia, New Zealand, Canada, Singapore, UAE, Saudi Arabia, or "other"), per-clinic currency/timezone/tax-mode defaults derived from that country, and Stripe billing (both clinic subscriptions and owner bill payments) for any clinic not billed in INR. Per your explicit instruction to keep global signup open rather than restrict it, I added (in `render.js`, shared across all 6 products' Privacy Policy pages, plus a one-line carve-out in the Terms pages' governing-law section): a lawful-basis statement (contract/consent/legitimate-interest/legal-obligation) and a supervisory-authority-complaint right for UK/EEA users, a no-sale/no-cross-context-sharing + know/delete/correct/non-discrimination statement for California residents, and an explicit (consent-based, not SCC-based - see below) cross-border-transfer acknowledgment. `entity.governingLawNote` in `data.js` was also reworded so it no longer flatly disclaims any jurisdiction-specific assessment while the new section right below it makes jurisdiction-specific commitments - it now says the international-users section takes precedence where the two conflict. Still needs a lawyer's actual review, specifically:
   - **International transfer mechanism.** The text uses explicit consent (GDPR Art. 49(1)(a)) as the transfer basis, since I don't know whether you have Standard Contractual Clauses or any other Art. 46 mechanism in place. Consent-based transfer is legitimate but regulators generally prefer it not be the sole basis for routine, repeated transfers (which this is, being every EU/UK signup) — ask a lawyer whether you need SCCs given expected volume.
   - **GDPR Article 27 EU/UK representative.** A company outside the EU/UK that processes EU/UK residents' data may need to appoint a local representative, subject to exemptions for occasional/low-risk processing that may or may not apply here. Not appointed, not mentioned in the published text (didn't want to assert an appointment that doesn't exist) — ask a lawyer whether you're in scope.
   - **DPO / EU rep contact channel.** Rights requests route to the same `support@animocentric.com` general inbox as the DPDP Grievance Officer — fine as a first version, but a GDPR-savvy reviewer may want a distinct channel or explicit confirmation the same inbox is adequate.
   - I did not add an EU "right to data portability in a machine-readable format" implementation detail (i.e., an actual export tool) — the text promises the *right*, but check whether you can currently fulfill a portability request in practice (manually is fine to start, but the promise should match reality).

5. **[PARTIALLY FIXED 2026-09-18] Stripe webhook signature verification gap.** `client-website/controllers/paymentController.js`'s `stripeWebhook` now refuses the request (503) when `STRIPE_WEBHOOK_SECRET` isn't configured and the server isn't in `development` mode, instead of silently trusting an unsigned body - closes the "forged webhook marks a bill paid" hole this note flagged. Still true and worth knowing: this endpoint's blast radius grew since this note was written - it now also activates/cancels clinic subscriptions (Stripe billing), not just owner bill payments, so the same forged-request risk this note called out for bill payments now applies to subscription state too. No code gap remains once `STRIPE_WEBHOOK_SECRET` is actually set in production - make sure that happens before Stripe goes live, not after.

6. **Server-side push (FCM) is not actually configured yet** (`FCM_SERVICE_ACCOUNT`/`FCM_SERVER_KEY` blank in `.env`) even though the Android apps already ship with a live Firebase project. The privacy pages describe the push feature as it will work once enabled, since the client-side data collection (push token) already happens regardless of whether the server sends anything. Nothing to fix in the legal text, just noting the gap so it doesn't surprise you later.

7. **SMS/WhatsApp reminders are described as not live** (stubbed in code, `TODO` in `utils/notifications.js`). If you turn on a real SMS/WhatsApp provider later, that provider needs to be added to `data/entity.json` and referenced in the relevant app's `thirdParties` in `data/apps.json`, and the policy regenerated — don't just flip the feature on in code without updating the privacy disclosure first, since notice-before-collection is the actual legal requirement, not notice-eventually.
